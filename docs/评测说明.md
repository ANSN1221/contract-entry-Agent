# 评测说明

## 怎么跑

```bash
# 单份
uv run python scripts/evaluate.py --gold eval/gold-DOC012.json

# 全部（PowerShell / bash 均可）
for g in eval/gold*.json; do
  echo "=== $g"
  uv run python scripts/evaluate.py --gold "$g" | tail -8
done
```

报告写到 `eval/report-<文档>.json`（已 gitignore），控制台同时打印逐字段对照表。

## 三个指标与失败含义

| 指标 | 分母 | 低了说明什么 |
| --- | --- | --- |
| 字段准确率 | 12 个字段 | 抽取或提示词有问题，也可能是标注口径不一致 |
| 引用可核对率 | 抽到值的字段 | 证据链断裂，值再对也不可信 |
| 不可答正确率 | 语料里没答案的问题 | 模型在编，最危险的一类 |

## 标注口径

1. **原文没写的填 `null`**，不做任何推断。例如 DOC004 没有质保期条款 → `warranty_period = null`，抽到值反而是错。
2. **术语按合同原文**，金标不替模型做同义转换。DOC012 的「缺陷责任期」不等于「质保期」时，模型没映射就算漏抽。
3. **数值宽松比较**：中文数字、百分比、千分位、日期格式差异都算等价（`百分之零点零五` = `0.05`，`2026 年 4 月 1 日` = `2026-04-01`）。
4. **文本用二元组覆盖率 0.7**：容忍虚词差异（原文「提起诉讼」vs 金标「诉讼」），但无关文本仍判错。

第 3、4 条本身有 21 条测试（`tests/test_eval_matcher.py`）——评测器错了，分数就是假的。

## 已知局限

- **样本量小**：4 份文档、48 个字段格。数字是方向性证据，不是统计结论。
- **语料分布偏窄**：都是政府采购类合同，施工/采购/服务三种，没有外企合同、框架协议、补充协议。
- **扫描件进不来**：16 份语料里 5 份是扫描件，需 OCR 才能纳入（当前直接跳过）。
- **只测抽取，不测端到端时长**：真实 PDF 上传解析耗时未计入。

## 怎么扩标注

1. 看 `F:/Contract-qa-RAG/data/processed/<DOC>.jsonl` 里的条款原文
2. 复制一份 `eval/gold-DOC012.json` 改字段值
3. 跑 `uv run python scripts/evaluate.py --gold eval/gold-<DOC>.json`

标注时如果发现**模型对但自己标错**，改金标并在 commit 里说明——这是评测集迭代的正常过程，比悄悄改分数诚实。
